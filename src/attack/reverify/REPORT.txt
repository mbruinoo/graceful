SUMMARY
I rebuilt the checks from scratch (tree search, placement enumeration, SAT, a deal search for spiders, Python certificate checkers) without reading growsolve.cpp, runsolve_gen.cpp or holes.cpp. Every README number in tasks (a)-(e) is reproduced exactly, with one exception: the section 11 table row "one run, at most one skipped cell on each side of the run" does not fail at n = 10. S(3,3,3) has an explicit build obeying that rule; the literal rule first fails at n = 18. The README figure matches a stricter rule in which, once all runs are singles, the leftmost single counts as the main run. Beyond the requested ranges: three-run placements certified for all trees with n <= 22; exactly one of the 5,623,756 trees on 22 vertices has no two-skip build, and it is the README's tree; Conjecture S certified for n <= 31. No proof of anything new; the conjecture remains open.

DEAD ENDS
1. SAT / CP as the main exhaustive engine: the CaDiCaL formulation takes 0.1-0.5 s per tree at n = 10-11 and 15-180 s on the hard negative instances at n = 16-22, so it cannot cover 123,867 trees at n = 18. It was used as a third method on all trees n <= 11 and on the named failure trees. OR-tools was installed but not used.
2. Placement enumeration as a second method for the 22-vertex two-skip failure: two-skip growth placements grow about 4.2x per vertex (38.8 million at n = 16), so roughly 2e11 at n = 22. Infeasible; the SAT run replaced it.
3. My first formalisation of 'at most one skipped cell on each side' (constraint only while a run of size > 1 exists) did not reproduce the README's n = 10 failure, and neither did a second 'tracked main run' formalisation that follows every reading of the build. The README number was only matched by the tie-breaking rule 'main run = first run of maximal size'. Smallest witness: S(3,3,3) at the state {2},{4},{6}.
4. The side-rule comparison used the author's compiled binary src/holes as a black box (run from a scratch directory, source not read). That is the only contact with the author's programs.
5. Not attempted: two-run counts at n = 22, B3 for n = 23-25, Conjecture S for n = 32-37, the sampled or large-family claims (n = 30-60, spherically symmetric trees), and sections 4, 9, 10 (slide graph, clean cuts, gap splits).
6. Operational: a background job hit a 30-minute limit mid-run (n = 22, H = 2); it was resumed from tree 3,600,001 rather than restarted, and the full output was re-checked.

===== CLAIM 1 [discrepancy]
STATEMENT
Discrepancy with README section 11, second table, row 3. The README says the rule 'one run, at most one skipped cell on each side of the run' first fails for one tree at n = 10, the spider S(3,3,3), with exhaustive range n <= 9. As stated, that is not reproduced: S(3,3,3) has a growth placement obeying the rule. Under the literal rule (unused labels are one run plus at most two isolated single labels, never two singles on the same side of the run), no tree with n <= 17 fails and exactly one tree with n = 18 fails: edges 1-0 1-2 0-9 2-3 3-4 3-7 4-5 4-6 7-8 9-10 10-11, and leaves 12..17 on 11. The README figure corresponds to a stricter rule: when all remaining unused runs are single cells, the first (leftmost) one is taken as 'the run', so three isolated singles are rejected because two lie to its right. Two smaller remarks, not errors: (i) the 22-vertex tree of section 11 has a two-run growth placement, which is sharper than the README's 'three runs when one hole has two cells'; (ii) one of the two 16-vertex trees without a two-run placement (a degree-3 vertex with arms of length 2, 2 and 5, each ending in a vertex with two leaves) has only two isomorphic branches at any vertex, which sits awkwardly with 'all its known failures are trees with three or more equal branches'; the other is centre plus three arms of length 2 each ending in three leaves.

EVIDENCE
gp.cpp with H=2 SIDE=2, in both the state-based and the tracked-main-run reading, finds a certified placement for every tree with n <= 17 and reports NONE for exactly one of 123,867 trees at n=18 (the same tree in both readings). Pure enumeration (enumgp H=2 SIDE=2) confirms: n=17, 54,226,312 placements draw all 48,629 shapes; n=18, 195,855,332 placements draw 123,866 shapes, missing exactly that tree. Identification of the README's rule: running (not reading) the author's binary gives 'holes 10 3 1 1' = 4,728 placements, 105 shapes and 'holes 11 3 1 1' = 17,220 placements; my probe_side.py reading 'each_leftmost' gives exactly 4,728 / 105 and 17,220, while the literal reading gives 6,192 / 106 and 23,556. The other holes modes match mine exactly (side-rule 0 = two skips: 6,884 and 28,788; side-rule 2 = same side: 5,672, 21,228, and 4,547,360 placements with 7,740 shapes at n=15), so the row 'both on the same side, first failure n=15' is confirmed. Remark (i): certificate for the 22-vertex tree with R=2, labels of vertices 0..21: 3 19 4 18 5 17 13 9 8 7 6 20 2 21 10 11 12 14 15 16 22 1.

PROOF
That S(3,3,3) obeys the stated rule is proved by exhibition. Labels 1..10, centre labelled 1, legs 1-10-3-8, 1-9-5-6, 1-7-4-2. Edge lengths: {1,10}=9, {1,9}=8, {3,10}=7, {1,7}=6, {3,8}=5, {5,9}=4, {4,7}=3, {2,4}=2, {5,6}=1, each of 1..9 once, decreasing outward on every leg (9,7,5 / 8,4,1 / 6,3,2), so by Theorem 7 it is a growth placement. The n = 18 failure and the absence of failures for n <= 17 are computer-verified only.
